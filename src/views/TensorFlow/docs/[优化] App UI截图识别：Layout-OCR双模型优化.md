# App UI截图识别：Layout-OCR双模型优化

本文是在上一篇【[指南] App UI截图识别：Layout-OCR双模型训练实战指南】的基础上，进一步引入 **Edge AI（边缘侧智能）** 方案。我们在前端集成了 Agent（智能体）、RAG（检索增强生成）及 **视觉工程优化** 策略，旨在解决传统 OCR 难以处理的重叠干扰、语义理解与逻辑校验问题。

## 背景

在上一阶段，我们成功部署了基于 YOLOv8 的布局检测与 CRNN 文本识别模型。但在实际应用中，单纯的“看图识字”仍存在瓶颈：

- **视觉干扰**：模型对同一文本块可能输出多个重叠框（Ghost Boxes），导致数据重复。
- **错别字干扰**：OCR 常将“内脏脂肪”误识为“内脏指肪”，导致正则匹配失效。
- **语义模糊**：无法区分“脂肪”（可能是体脂率）与“皮下脂肪”等包含关系词汇。
- **逻辑错误**：识别出的数值可能违背物理常识（如人体水分率 > 100%）。

为了打破这些僵局，我们构建了 **视觉清洗 (Vision)** -> **语义增强 (RAG)** -> **逻辑修正 (Agent)** 的三级保障体系。

## 🛠️ 实战一、视觉层精调 (Vision Layer)

在数据进入 AI 逻辑分析之前，首先要确保“眼睛”看清楚。针对 YOLO 模型常见的重叠框和漏检问题，我们在 `src/services/ocr/core/layout.ts` 中实施了严格的 **NMS (非极大值抑制)** 与参数治理。

这属于**推理参数调优 (Inference Tuning)**，而非模型权重微调。

1.  **NMS 去重 (Ghost Box Removal)**：
    利用 `tf.image.nonMaxSuppressionAsync` 剔除冗余框。
    - **参数策略**：针对密集文本排版，我们将 `IOU_THRESHOLD` 调高至 `0.6`（允许文字紧邻），并将 `MAX_OUTPUT_SIZE` 提升至 `200`，防止复杂体检报告中后半部分内容被强制截断。
2.  **动态阈值 (ROI Adaptive Threshold)**：
    针对“日期”等位于特定区域（如屏幕中下部）的小字容易漏检的问题，我们没有重新训练模型，而是采用 **ROI (感兴趣区域)** 策略，在代码逻辑中动态降低该区域的置信度门槛，用规则弥补模型的“视力”缺陷。

## 🛠️ 实战二、引入前端 RAG (语义层)

为了解决 OCR 的“胡言乱语”（如错别字、非标准命名），我们在 `src/services/ocr/rag/` 下构建了一个轻量级的向量检索系统。

### 1. 核心架构设计

我们在前端引入了 Transformers.js，加载支持中文的 Embedding 模型（`paraphrase-multilingual-MiniLM-L12-v2`），实现了纯前端的语义匹配。

- **`embedding-engine.ts` (核心引擎)**：
  - 实现了 **Singleton (单例模式)** 与 **Lazy Loading (懒加载)**，确保 90MB 的模型文件仅在用户开启功能时下载，且全局唯一。
  - 支持 **WebGPU 加速**，在现代浏览器中实现毫秒级的向量计算。
  - 设计了 **Promise 锁**，防止页面刷新或并发调用导致的初始化死锁。

- **`semantic-matcher.ts` (匹配逻辑)**：
  - **向量库构建**：将项目中的标准指标名（Key）转化为向量存储。注意，这里我们保持了向量库的纯净，**不存储**“标准”、“偏高”等状态词作为负样本。
  - **阈值拦截 (Threshold)**：设定高相似度阈值（如 0.82）。当 OCR 识别出“标分”时，因其与“体型”的相似度仅为 0.55，会被 RAG 自动拦截并丢弃，从而避免了语义误判。
  - **长度惩罚 (Length Penalty)**：为了解决包含关系（如“脂肪”vs“皮下脂肪”），引入算法惩罚。当 OCR 文本与标准词长度差异过大时，强行扣除相似度分数，防止短词越级匹配。

### 2. 业务流程融合

在 `parser.ts`（编排层）中，我们改造了核心的分类函数 `classifyBoxes`，采用了 **"规则优先，AI 兜底"** 的混合策略：

1.  **Rule-Based (L1)**：优先匹配 `startsWith` 或 `includes` 命中的确切关键词，保障高性能。
2.  **RAG-Based (L2)**：当规则未命中，且开启了 `useRAG` 配置时，调用语义匹配。
    - OCR 识别为“内脏指肪” -> RAG 计算向量 -> 匹配到“内脏脂肪” -> **自动修正**。
3.  **配置透传**：通过 UI 层的 Switch 开关，将 `useRAG` 参数一路透传至 Parser，实现功能的按需开启。

## 🛠️ 实战三、加入Agent修正(逻辑层)

Agent 是一个具备“观察-思考-行动”能力的逻辑实体。在 `src/services/ocr/weight-domain/ocr-agent.ts` 中构建了四重防御策略链，由轻到重层层过滤异常：

1.  **上下文公式修正 (Context Logic)**：利用同屏数据的关联性（如 `建议 - 当前 = 控制`），当 OCR 数值符号错误时，优先信赖公式计算结果。
2.  **历史范围修正 (History Magnitude)**：基于 `history-analyzer.ts` 分析的用户历史数据中位数。针对 OCR 常见的小数点漂移错误（如 `54.5` 变 `545`），Agent 会尝试进行 `/10` 或 `/100` 的回归测试，若回归后落入历史合理区间，则自动采纳。
3.  **物理极限兜底 (Physical Limits)**：针对冷启动用户，引入人类生理极限常识（如 BMI 不可能 > 100）。这是防止离谱错误的最后一道防线。
4.  **激进模式重试 (Aggressive Retry)**：当上述软修正失效且数值依然异常时，Agent 会主动调度 `src/services/ocr/core/ocr-engine.ts`，开启**二值化**与**大 Padding** 参数重新截图识别。

## 📁 服务层结构概览

为了更好地组织代码结构📁，我们将OCR识别服务层拆分成多个模块，每个模块负责特定的功能。具体拆分如下：

```text
src/services/ocr/
├── index.ts                # [Facade] 对外暴露 runRecognition, initializeModels
├── types.ts                # [Type] 类型定义
├── config.ts               # [Config] 包含标准模式/激进模式配置
├── core/                   # [Core Layer] AI 基础设施
│   ├── model-state.ts      # 单例管理 (TFJS/ONNX Session)
│   ├── layout.ts           # YOLOv5 预处理与后处理
│   └── ocr-engine.ts       # CRNN 原子推理能力 (支持不同Config)
├── utils/                  # [Utils Layer] 纯函数工具
│   ├── math.ts             # 数学计算 (两个向量的余弦相似度)
│   └── geometry.ts         # 几何计算(isSameLine) & 字符串清洗
├── debug/                  # [Debug Layer] 开发者工具
│   └── tools.ts            # Canvas可视化 & 数据集Zip打包
├── rag/                    # [Core Layer] AI 基础设施
│   ├── embedding-engine.ts # [Core] 模型加载器 (Transformers.js, WebGPU加速, 单例锁)
│   └── semantic-matcher.ts # [Logic] 语义匹配器 (向量库构建, 阈值过滤, 长度惩罚)
└── weight-domain/          # [Domain Layer] 业务逻辑层
    ├── constants.ts        # 静态数据 (关键字、映射表)
    ├── history-analyzer.ts # 历史数据分析 (动态范围计算、时间衰减逻辑)
    ├── parser.ts           # 编排器：融合 规则分类 + RAG 语义纠错 + 几何配对
    └── ocr-agent.ts        # 智能体：多策略修正 (Context/History/Physics) + 主动重试
```

## ✏️ 关键经验与反思

### 1. 关于“模型微调 (Fine-tuning)”的决策反思

在本项目中，我们**最终放弃了在前端进行模型权重的训练（Training）**，原因如下：

- **灾难性遗忘**：前端 YOLO 是单类别模型。若为了识别“日期”而强行喂入只有日期的图片进行训练，模型会迅速忘记如何识别“体重”和“BMI”。
- **架构限制**：前端无法修改模型架构（如增加一个输出类别）。
- **最佳实践**：我们选择了 **参数调优 (Parameter Tuning)** 代替 **模型微调 (Model Fine-tuning)**。即通过 NMS、ROI 阈值调整和输入尺寸优化（`config.ts`）来解决漏检问题。这证明了**工程化手段往往比盲目训练更高效**。

### 2. RAG 与 Agent 的边界

- **RAG** 负责“翻译”，解决的是 OCR 导致的字面错误。
- **Agent** 负责“审判”，解决的是数值逻辑和业务合理性问题。
- 两者各司其职，配合 NMS 清洗后的干净数据，构成了完整的端侧智能链路。

### ⚖️ 3. 局限性与反思 (Limitations)

尽管我们引入了 AI 组件，但为了在前端（Edge Side）保持高性能和低延迟，我们对 RAG 和 Agent 的实现均做了工程化的“剪裁”。理解这些局限性有助于明确系统的能力边界。

### 1. RAG 的“缺失之环”：只有检索 (Retrieval)，没有生成 (Generation)

在标准的 RAG 架构中，通常包含“检索上下文”和“LLM 生成回答”两个步骤。
但在本项目 `src/services/rag/` 中，我们**阉割了 Generator（生成器）**：

- **当前实现**：本质是 **Semantic Search (语义搜索)**。我们利用 `embedding-engine.ts` 计算向量，通过 `semantic-matcher.ts` 找到距离最近的标准词（Key）。我们只用它来做**分类**（Classify）和**映射**（Map）。
- **功能缺失**：
  - **无法解释原因**：系统只能将“内脏指肪”修正为“内脏脂肪”，但无法告诉用户“为什么修正”（例如无法输出：“检测到‘肪’字为常见错别字...”）。
  - **无法处理非结构化查询**：无法回答用户诸如“我的各项指标中哪个最不健康？”这类需要综合理解并生成自然语言的问题。
- **改进方向**：若需完整的 RAG 体验，需引入 WebLLM 或云端 LLM API，将检索到的上下文喂给模型进行文本生成。

### 2. Agent 的“认知天花板”：规则型 (Heuristic) vs 认知型 (Cognitive)

目前的 `ocr-agent.ts` 虽然被称为 Agent，但它本质上是一个**高级的状态机 (Advanced State Machine)**，而非基于 LLM 的自主智能体。

- **当前实现**：
  - **确定性逻辑**：Agent 的行为完全由代码中写死的策略链（`strategyContextSign`, `strategyHistory`）决定。它依然是 `if-else` 的堆叠，只是逻辑更复杂。
  - **零泛化能力**：如果 App UI 出现了一种全新的逻辑关系（例如“骨量 + 肌肉量 = 去脂体重”），除非程序员手动修改 `ocr-agent.ts` 添加新策略，否则 Agent 永远无法“顿悟”出这个公式。
- **功能缺失**：
  - **缺乏规划能力 (Planning)**：真正的 AI Agent (如 ReAct 模式) 能够根据目标自动拆解步骤（例如：“发现数字模糊 -> 决定先切图 -> 再二值化 -> 再识别”）。而我们的 Agent 只能按预设顺序重试。
  - **无法理解自然语言指令**：无法响应用户的动态指令（如：“请只关注红色的数字”）。
- **改进方向**：要升级为真正的 Agent，需要将 `parser.ts` 中的逻辑编排权交给一个小型的 LLM，让模型根据当前的 Observation（观察）动态决定下一步 Action（行动），但这将带来巨大的性能开销。

---

### 总结 ✏️

当前的架构是在 **“工程实用性”** 与 **“AI 灵活性”** 之间做的完美折中。我们利用 **NMS 让眼睛看清楚**，利用 **RAG 让脑子理解语义**，利用 **Agent 让逻辑回归理性**，同时避免了高昂的端侧训练成本。

- **RAG** 退化为 **语义匹配**，换取了毫秒级的纠错速度。
- **Agent** 退化为 **启发式策略**，换取了 100% 的可控性和稳定性。

这正是 Edge AI（端侧智能）落地的典型特征：**用这一代的技术架构，解决上一代（纯正则/纯规则）无法解决的死角，同时避免引入下一代（纯大模型）过高的算力成本。**
