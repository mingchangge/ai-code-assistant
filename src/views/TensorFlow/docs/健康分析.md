# 前端健康分析：从逻辑 Agent 到端侧混合智能

## 1. 核心设计理念：混合智能 (Hybrid Edge AI)

本架构的核心在于 **“快慢结合，端侧闭环”**。我们将分析任务分层处理，利用浏览器的一切算力（CPU & GPU），实现零后端依赖的极致体验。

- **L1 瞬时层 (Logic/CPU)**：基于 **LangChain Agent** 和 **混合 RAG**。毫秒级响应，负责数学趋势计算、标准比对。解决“准确性”和“速度”问题。
- **L2 深度层 (Reasoning/GPU)**：基于 **WebLLM** (Worker 隔离)。秒级响应，负责自然语言生成、深度建议。解决“个性化”问题。
- **高可用策略 (Resilience)**：独创 **“缓存优先 -> 网络探测 -> 本地兜底”** 的三级加载策略，彻底解决 HuggingFace 连通性差、CORS 跨域及断网问题。

## 2. 完整目录结构与职责划分

我们将工程 📂分为 **Worker 线程**（重计算）和 **主线程 Service**（逻辑调度）两部分：

```text
src/
├── workers/
│   └── llm.worker.ts                 # [Kernel] LLM 推理核心与加载策略路由，独立线程运行 (L2)
└── services/
    ├── ocr/                         # [OCR Layer] 光学字符识别模块
    │   └── rag/
    │       └── embedding-engine.ts   # [Core] 底层 WebGPU 向量化引擎 (OCR/RAG 共享)
    └── advisor/
        ├── index.ts                  # [Facade] 服务门面，统一 API，协调 Agent(L1) 与 LLM(L2)
        ├── types.ts                  # [Model] 领域模型定义
        ├── config/                  # [Brain] 业务大脑
        │   ├── metrics.ts            # **核心配置**：指标元数据、阈值、RAG 路由规则
        │   └── llm-config.ts         # [Env] 模型环境配置 (定义模型 ID、本地/网络模式开关、降级策略参数)
        ├── core/                    # [Tools] 纯函数工具箱
        │   ├── llm-service.ts        # [Bridge] 主线程桥梁 (负责单例管理、任务锁、预加载信号)
        │   ├── trend-math.ts         # [Math] 线性回归与趋势判定引擎
        │   ├── data-cleaner.ts       # [Cleaner] 数据清洗与标准化
        │   └── chart-factory.ts      # [Vis] 可视化配置工厂
        ├── rag/                     # [Knowledge] 知识检索层 (L1)
        │   ├── vector-store.ts       # [Store] 混合检索逻辑 (向量相似度 + 硬规则过滤)
        │   ├── langchain-adapter.ts  # [Adapter] LangChain 接口适配器
        │   └── knowledge-base.ts     # [Data] 结构化本地知识库
        └── agent/                   # [Pipeline] 逻辑调度层 (L1)
            ├── tools.ts              # [Tool] 工具封装
            ├── prompts.ts            # [Prompt] 提示词工程
            └── health-agent.ts       # [Engine] 基于 LCEL 的并行流水线引擎
├── scripts/
│   └── download-model.js     # [DevOps] 零依赖模型自动化部署脚本 (Postinstall Hook)
└── public/
    └── models/               # [Assets] 本地模型仓库 (GitIgnored, 仅在构建/安装时生成)
```

### 注释补充说明：

1.  **`llm.worker.ts`**: 标记为 `[Kernel]`，强调它是耗时计算的核心，且通过 `独立线程` 保证了主 UI 的流畅。
2.  **`embedding-engine.ts`**: 标记为 `共享模块`，意味着 OCR 和 RAG 可能复用同一个轻量级模型来提取特征向量。
3.  **`config/metrics.ts`**: 标记为 `[Brain]`，因为所有的业务规则（如“体重该看趋势还是看数值”）都内聚在这里，体现了配置驱动的思想。
4.  **`llm-service.ts`**: 标记为 `[Bridge]`，它的职责不是推理，而是“管理”——管理 Worker 的生命周期、消息队列和 Promise 锁。
5.  **`health-agent.ts`**: 标记为 `[Engine]`，它使用 LCEL 将原本零散的工具（Tools）串联成并行流水线，是 L1 层的调度中心。

## 3. L1 逻辑层详解：Agent 与 RAG

这一层运行在主线程，利用 CPU 进行快速逻辑运算，是系统的基石。

### A. 基于 LCEL 的并行流水线 (Agent Pipeline)

**涉及文件**：`src/services/advisor/agent/health-agent.ts`

我们摒弃了手写循环，使用 **LangChain Expression Language (LCEL)** 构建了类型安全的处理链：

1.  **Map Runner**：利用 `RunnableLambda` 实现真·并行处理。Math 计算与 RAG 检索并发执行，极大降低延迟。
2.  **Micro Chain**：每个指标的处理逻辑被封装为原子链：`Math Tool` -> `Metric Config` -> `RAG` -> `Format`。

    > **意义**：结构清晰，天然支持 Trace 调试，且为未来扩展留出接口。

### B. 混合检索机制 (Hybrid RAG)

**涉及文件**：`src/services/advisor/rag/vector-store.ts`

为了解决纯向量检索“不懂数学边界”的痛点，我们设计了 **“向量 + 规则”** 双重保障：

1.  **第一轮：严格匹配 (Strict Mode)**
    - **语义搜索**：计算向量相似度。
    - **硬规则过滤**：强制匹配 `Gender`, `Category`。
    - **数值围栏**：强制要求当前数值落在知识库定义的 `valueRange` (闭区间) 内。
2.  **第二轮：兜底匹配 (Fallback Mode)** - 当数值落入“真空区”时，自动放宽条件，仅匹配分类和性别，返回通用建议。
    > **意义**：既有向量检索的语义理解，又有代码逻辑的精准控制，确保 0 幻觉。

### C. 配置驱动的路由

**涉及文件**：`src/services/advisor/config/metrics.ts`

Agent 代码中无硬编码。所有逻辑由配置决定，例如体重指标配置了 `ragConfig: { useDiffValue: true }`，Agent 就会自动去检索“变化值”而非“绝对值”的建议。

## 4. L2 深度层详解：Edge LLM 与 Worker (重要升级 🌟)

这一层运行在 Worker 线程，利用 WebGPU 调用本地显卡资源，是系统的“大脑”。

### A. 线程隔离与状态机路由

**涉及文件**：`src/workers/llm.worker.ts`

这是架构中最重要的性能优化点。

1.  **Web Worker 隔离**：模型加载、Shader 编译、矩阵运算全部在 Worker 中完成。主线程仅收发文本。这意味着即使模型占满 GPU，**UI 依然可以以 60fps 流畅响应**。
2.  **Switch-Case 状态机**：摒弃简单的 `if-else`，使用 Switch 结构处理 `init` 和 `generate` 指令，配合 TypeScript 类型收窄，确保通信协议严谨、可维护。

### B.三级自动降级加载策略 (Failover Strategy)

**涉及文件**：`src/workers/llm.worker.ts` -> `resolveModelConfig`
为了应对不稳定的网络环境，我们摒弃了单一加载源，实现了智能路由：

1.  **Cache First (L1)**：优先询问 WebLLM “本地缓存有没有？”。如有，**跳过所有网络请求**，直接离线加载（秒开）。
2.  **Network Check (L2)**：
    - 探测 `HuggingFace` -> 失败则探测 `hf-mirror.com` (国内镜像)。
    - 采用 `HEAD` 请求 + 2s 超时控制，防止页面卡死。
3.  **Local Fallback (L3)**：
    - 若全网不通，降级指向 `public/models` 下的本地静态文件。
    - 通过 `self.location.origin` 构造同源绝对路径，**彻底根治 CORS 问题**。

### C. 通信节流 (Throttling)

**涉及文件**：`src/workers/llm.worker.ts`

WebLLM 下载模型时每秒触发数百次回调。我们在 Worker 内建立缓冲池：

- **策略**：仅当进度整数位变化 (如 1% -> 2%) 或状态文案变更时，才向主线程 `postMessage`。
- **效果**：主线程消息处理量减少 99%，消除 UI 掉帧。

### D.任务锁与竞态保护

**涉及文件**：`src/services/advisor/core/llm-service.ts`

我们使用单例模式管理模型生命周期，并引入了“任务锁”机制：

1.  **竞态保护**：`initPromise` 作为一个锁。如果用户在模型下载到一半时点击“分析”，`generateReport` 方法会自动 `await initPromise`。
    - **效果**：用户不会遇到报错，程序会自动等待下载完成后，无缝衔接进入生成阶段。
2.  **资源复用**：模型一旦加载，常驻内存。后续分析无需重新加载。

### E. (新增) 本地模型交付闭环

**涉及文件**：`scripts/download-model.js`
为了配合 **Local Fallback (L3)** 策略，我们需要确保用户的 `public/models` 目录下一定有文件。我们摒弃了昂贵且受限的 Git LFS，采用了 **"GitHub Releases + Postinstall Script"** 方案：

1.  **Release 托管**：利用 GitHub Release 支持 2GB 附件的特性，将模型打包为 ZIP 托管，规避 Git 100MB 限制。
2.  **自动化部署**：`npm install` 后自动触发下载脚本，实现“开箱即用”。

## 5. L3 交互层详解：UI/UX 优化模式

### A. 静默预加载 (Silent Preload)

**涉及文件**：`Dashboard.tsx`, `index.ts`

**策略**：

1.  **错峰计算**：当用户进入页面浏览 L1 层生成的“基础图表”时，系统在后台悄悄调用 `preload()` 启动 Worker 进行模型下载和编译。
2.  **按需生成**：当用户点击“AI 深度分析”按钮时，模型往往已经就绪（或下载了大半），实现了“点击即响应”的体感速度。

### B. 渲染节流 (Render Throttling)

**涉及文件**：`Dashboard.tsx`

**原理**：
LLM 生成速度很快（流式输出）。如果每个 Token 都触发 React 的 `setState`，会导致组件高频重绘，消耗大量 CPU。

**优化方案**：
引入 `useRef` 缓冲区。将 Token 存入 Buffer，仅当距离上次渲染超过 **100ms** 时，才真正触发 React 更新。

> **意义**：在人眼无感的情况下，大幅降低了 React 的渲染压力，消除了打字机效果时的卡顿。

### C. 语义化展示

**涉及文件**：`AnalysisCard.tsx`

前端组件深度结合配置：

- **颜色语义**：根据 Config 中的 `type: 'min'` 自动判断指标是“越大越好”还是“越小越好”，从而决定红色/绿色的语义（例如肌肉量增加显示绿色，体脂率增加显示红色）。

### D. 智能进度可视化 (Regex Parsing)

**涉及文件**：`Dashboard.tsx` -> `translateProgress`
解决了原生日志体验差的问题：

1.  **缓存加载修正**：原生日志显示 `0%` 直到结束。我们通过正则提取 `[current/total]` 手动计算真实百分比，实现平滑进度条。
2.  **语义翻译**：将 `Fetching param cache` 实时翻译为“📥 正在下载模型资源...”，将 `Loading GPU shader` 翻译为“⚡️ 正在编译着色器...”。

### E. 智能视口跟随 (Smart Viewport Tracking)

**涉及文件**：`Dashboard.tsx`
引入 **`react-sticky-box`** 库，摒弃了传统的 `CSS Sticky` 或 `Max-Height` 滚动条方案。

- **痛点解决**：当右侧内容高度超过视口（Viewport）时，原生 `sticky` 会导致底部内容被截断且无法查看。
- **交互逻辑**：实现了 **"Natural Scroll + Edge Sticky"** 模式。
  - 向下滚动时：内容自然上移，直至底部边缘触达视口底部后吸附 (Bottom Sticky)。
  - 向上回滚时：内容自然下移，直至顶部边缘触达视口顶部后吸附 (Top Sticky)。
- **价值**：彻底消灭了页面的“双重滚动条”，在保持左右布局同步的同时，提供了符合直觉的原生级浏览体验。

### F. 异常恢复机制 (Retry Pattern)

**涉及文件**：`handleStartAnalysis`
虽然有自动预加载，但我们依然保留了按钮点击时的状态回调。

- **目的**：当预加载因断网失败（按钮变红）时，用户点击“重试”，该回调能实时更新界面进度，提供“正在重试下载”的反馈，避免“点击无反应”的假死状态。

## 6. 工程化与部署策略 (Engineering & DevOps) 🛠️

这部分解决了 AI 前端项目最大的痛点：**大模型文件的版本管理与分发**。

### A. 零依赖动态引导 (Dynamic Bootstrap)

**涉及文件**：`scripts/download-model.js`
脚本采用 **Self-Healing (自愈)** 设计，不依赖用户预先安装任何工具：

- **动态依赖注入**：脚本运行时检测 `adm-zip` 是否存在。若不存在，自动调用 `npm install --no-save` 临时安装。
- **Top-level Await**：利用 Node.js 新特性实现流畅的异步安装流程。
- **价值**：新成员 `git clone` 后只需执行 `npm install`，无需任何额外操作即可获得完整的 AI 运行环境。

### B. 安全的中转解压策略 (Staging Area Strategy)

为了防止下载/解压过程污染或误删开发者本地已有的模型文件，脚本实现了 **原子化操作**：

1.  **Download**：下载 ZIP 到临时路径。
2.  **Staging**：解压到 `temp_staging_area` 中转目录。
3.  **Rename & Move**：在中转区内识别真实根目录，重命名为目标配置名（如 `..._123`），最后**原子移动**到 `public/models`。
4.  **Cleanup**：无论成功失败，强制清理临时文件。
    > **效果**：既保留了开发者本地的旧模型备份，又确保了新下载模型的完整性，杜绝了“解压了一半报错导致文件损坏”的情况。

### C. 网络加速与断点防御

针对国内网络环境的特殊优化：

1.  **Mirror Proxy**：脚本内置 `ghproxy` 加速源，解决 GitHub Release 下载超时/断连问题 (`ECONNRESET`)。
2.  **Stream Processing**：使用 NodeJS Stream 管道处理 1GB+ 文件，避免内存溢出 (OOM)。

## 7. 总结

这套架构通过精细的 **分层设计 (L1/L2)** 和 **线程管理 (Worker)**，成功解决了在浏览器端运行复杂 AI 应用的性能瓶颈。

它不仅仅是一个功能的堆砌，更是一次对 **Edge AI (端侧智能)** 落地场景的深度工程实践：**让严谨的数学逻辑与先进的大模型推理在浏览器中共存，且互不干扰、相辅相成。** 现在，我们不仅拥有了 **Worker 隔离**的运行性能、**三级降级**的加载可靠性，还拥有了 **一行命令 (`npm install`)** 即可完成环境搭建的极致开发体验。
